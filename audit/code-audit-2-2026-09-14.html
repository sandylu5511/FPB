一、本轮修复的 6 处缺陷

#1 P1不可读/缺失的条目 id 在下一次写入时被静默从清单抹掉

改前（VaultSession.kt loadIndex/persistIndex）：

// 损坏行只进报告，不进任何持久结构
if (row == null) { missing++; continue }
if (payload == null) { unreadable++; continue }
...
// persistIndex 只写 index.keys —— broken id 不在其中
val listBytes = NoteIndexCodec.encode(index.keys.toList())

改后：

private val brokenIds = LinkedHashSet<String>()  // 清单里存在但缺失/解不开的 id
if (row == null) { missing++; brokenIds.add(id); continue }
if (payload == null) { unreadable++; brokenIds.add(id); continue }
...
val listBytes = NoteIndexCodec.encode(index.keys.toList() + brokenIds)
// 容量检查同步计入：val next = index.size + brokenIds.size + adding
用户感知差异损坏条目的问题持续可见：解锁时提示"1 条不可读"，此后每次解锁都继续报，直到用户处理；修复前是"新建任意一条笔记后问题凭空消失"。
风险触发条件：任一条目密文损坏或行丢失后发生任何写入。修复前后果：不可逆——该行的域归属凭证（清单是唯一凭证）永久丢失，行变成无法归属、无法清理、无法被另一库认领的永久孤儿。触发概率低（需介质损坏），但数据完整性设计目标被击穿。

#2 P1索引清单编码器不校验 id 形状（自锁清单类缺陷）

改前（NoteIndexCodec.kt encode）：

require(ids.size <= MAX_ENTRIES) { ... }
// 对 id 本身零校验 —— "zzz" 也能写进去

改后：

ids.forEach { id ->
    require(RowIds.isValid(id)) { "清单 id 形状非法（应为 32 位十六进制）：$id" }
}
用户感知差异无直接感知（当前生产路径的 id 源全部合法，属潜在缺陷）。修复的是防线位置：从"所有调用方永远不犯错"移到"能写坏数据的那一侧"。
风险与第一轮修掉的"MAX_ENTRIES 只查解码侧"同类：一旦写出一份含非法 id 的清单，下次解锁判定"清单不可读"，整库锁死且无补救途径。当前为潜在路径（自定义 idFactory、将来的备份导入会引入外部 id）。

#3 P2密钥文件解码不检查尾部多余字节

改前（VaultKeyFile.kt decode）：读完最后一个槽位即返回，追加的任意字节被静默忽略。且第一轮测试 尾部被追加垃圾字节仍能解码 把这个缺陷固化成了预期行为。

改后：

if (input.available() != 0) {
    throw VaultKeyFileException("密钥文件尾部存在 ${input.available()} 字节多余数据（可能被篡改或格式不匹配）")
}

同步把旧测试翻转为 尾部被追加垃圾字节应被拒绝（基线上它失败，修复后通过）。

用户感知差异导入被拼接/篡改过的备份密钥文件时，得到明确报错而不是"静默接受一个来源可疑的密钥文件"。
风险触发条件：导入不可信备份包（M5 场景）。NoteCodec 与 NoteIndexCodec 都有此检查，唯独密钥文件漏了——密钥文件恰是三者中输入最不可信的一个。

#4 P2笔记编解码不校验 blobId 形状（防线分散）

改前：编码接受任意字符串当 blobId；解码原样放行。每个使用点（image()/deleteImage()/FileBlobStore.fileFor()）各自做 RowIds.isValid 防御——防线存在但分散，脏引用会进内存索引长期存活。

改后：编码侧 require、解码侧整条笔记判为不可读（走 LoadReport 的 unreadableRows 报告通道，不静默）。

用户感知差异无直接感知（当前无路径能产出非法 blobId）。防线从"每个 UI 使用点各自记得防"收敛为"入库即拒绝"。
风险低——路径穿越本身一直被挡（fileFor 拼路径前校验）。修复属于防御纵深前移 + 编解码对称性。

#5 P2putImage 无明文体积上限（第一轮已知项，本轮补上）

改前（VaultSession.putImage）：任意大小的明文字节直接加密落盘。

改后：

const val MAX_IMAGE_PLAINTEXT_BYTES = 32 * 1024 * 1024  // 32 MiB
require(plaintext.size <= MAX_IMAGE_PLAINTEXT_BYTES) { "图片明文 ${plaintext.size} 字节超过上限..." }
用户感知差异正常重编码图片（长边 2048 / JPEG q85，约 1~3 MB）不受影响；异常巨图得到明确报错，而不是入库后拖垮每次解锁、或让低端机在解密时 OOM。
风险触发条件：上游图片管线忘记压缩（M3 接入时的真实风险）。恰好等于上限的图片仍可用（有正向测试）。

#6 P2create() 的 id 冲突静默覆盖已有条目（防御加固）

改前：新 id 不查重。idFactory 返回已有 id 时，旧条目的内存索引与磁盘密文被同时替换，无任何异常。

改后：

check(id !in index) { "生成的条目 id 与现有条目冲突，拒绝覆盖：$id" }
check(id != manifestRowId()) { "生成的条目 id 与清单行冲突，拒绝覆盖：$id" }
用户感知差异无直接感知（128 位随机 id 碰撞概率约等于零）。将来备份导入引入外部 id 时，碰撞表现为大声报错而非静默丢数据。
风险潜在路径：测试用自定义 idFactory、M5 备份导入。第二条 check 同时挡住"笔记行写到清单行 id 上"（会覆盖"哪些笔记存在"的唯一凭证）。

二、本轮的元发现：测试也可能为缺陷背书

VaultKeyFileTest.尾部被追加垃圾字节仍能解码 是一条把缺陷当预期行为写进测试的用例（注释原文："追加垃圾不影响解析：读取按长度字段推进，多余部分自然被忽略"）。它让第一轮审核（含上一轮的我自己）接受了"密钥文件不查尾部字节"这个行为——因为有一个绿灯在给它背书。

教训已并入审核技能：审"生产代码缺校验"的同时，必须反向审"测试是否在断言缺陷行为"。判别法：找所有名字里含"仍能/仍然/不影响/可以继续"的测试，逐条问"这真的是设计意图，还是当时实现恰好如此"。

三、修复过程中再次踩到的工具坑（已二次证实）

同一文件的多条编辑会被静默丢弃——工具报告成功但内容未变。本轮 VaultSession.kt 的 6 处编辑中 3 处被丢弃（create 冲突检查、putImage 上限、容量计数含 brokenIds），前两处靠测试失败暴露，第三处连测试都没能暴露（该分支无测试覆盖），最终靠 grep 复核发现。处置：

  • 本轮所有编辑已改为"单条编辑 → 立即 grep 验证"流程；
  • 诚实披露：容量修复（#1 的组成部分）是在全量测试通过之后才补落盘的，随后重跑了全量 143/143 + 重建 APK + 真机自检 19/19，证据为最终一轮；
  • 该分支的残余缺口：容量检查含 brokenIds 的组合场景没有专门测试（构造 10 万条目 + 损坏组合在单测里代价过高），但有硬兜底——NoteIndexCodec.encode 的编码侧上限检查会让事务回滚，不会写出自锁清单。

四、未修改但需知晓（设计权衡，刻意不修）

项为什么不修修了会误伤什么
loadIndex"清单行不存在 = 全新库"的模糊判断 两种情况字节层面不可区分；写入侧事务已把窗口关到只剩介质损坏 改成"库里有行就拒绝解锁"会让诱饵库首次打不开（真库有行、诱饵库还没写过），胁迫防护被废
update() 移除图片后不立即删 blob 用户撤销"移除图片"的操作需要可恢复；孤儿密文无害且可被 purgeOrphanBlobs 清理 立即删除会让误操作不可逆——图片是全应用唯一不可再生数据
KDF 参数上限 1 GiB（低内存设备仍可能 OOM） 上界已从无界收紧到 1 GiB；正常备份文件只会带预设档位参数 收紧到手机安全值会让"高安全档 256 MiB"在某些设备的合法备份被拒
AAD 无长度前缀（理论上 "a:b"+"c" 与 "a"+"b:c" 可碰撞） 参与 AAD 的 id 全部是 32 位定长十六进制、field 是内部常量，实际无歧义 改格式会作废所有已落盘密文
Aad.manifest() / isPlausiblePartialInput() / storageBytes() / deleteImage() 当前无生产调用方 均为 M3（设置页/输入框）/M5（备份导出）预留；自检与测试有引用 删除后再加回来徒增变更噪音
解密后密码 CharArray 未在调用方清零（自检与测试路径） 生产 UI（M3）接入时统一处理更合适 现在改测试代码无收益

五、确认无误的部分（避免"只列问题 = 代码全是问题"）

  • 真/假库隔离链路完整：域标记编译期防写错槽、AAD 防密文搬运、解锁双槽同试不短路、purgeOrphanBlobs 仅认"当前域 DEK 解得开的附件"——本轮未发现新绕过。
  • 事务原子性（第一轮修复后）：create/update/delete 的行+清单同事务，Fakes 实现真实回滚；真机自检"重开后完整恢复"持续通过。
  • Base32Crockford / RecoveryCode：别名输入、容错映射、往返唯一性在上轮修复后无回归。
  • NoteCodec 解码器的防御立场：长度对 available() 的预检查、尾部干净检查、异常吞掉不泄细节——结构良好。
  • 权限与落盘形状：无 INTERNET 权限、allowBackup=false、数据库三列纯密文、附件目录随机文件名——独立 grep 0 命中复验通过。
  • SQLite 层：占位符 SQL、BEGIN/END 事务配对、REPLACE 语义不踩 FK 陷阱（表无外键）。
