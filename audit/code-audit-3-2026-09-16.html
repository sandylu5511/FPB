一、本轮修复的 5 处缺陷

严重级含义：P1会造成数据丢失或功能整体失效； P2在特定场景下出错、可绕过但有代价；P3观感或维护性问题。

P1#1 全应用的"操作反馈与错误提示"等于没有显示

现象.点「导出备份」成功后没有任何提示；失败时也没有。所有"已导出 12 条记录"、"保存失败：…"、 "导入失败：…"都只是闪一下 —— 而 setMessage() 在全应用有 55 处调用，其中包括所有错误分支。

根因.承载提示的 LaunchedEffect 把自己的 key 设成了 state.notice， 却在 effect 体内把它置空：

改前（ui/AppRoot.kt）
val hostState = remember { SnackbarHostState() }
LaunchedEffect(state.notice) {              // ← key 是提示文案
    val text = state.notice ?: return@LaunchedEffect
    state.notice = null                     // ← 在体内改掉了自己的 key
    hostState.showSnackbar(text)
}

key 从"文案"变成 null，Compose 按语义取消并重启这个协程；而 showSnackbar 一旦被取消，Snackbar 会被立刻撤下（它的 finally 会清 currentSnackbarData）。

改后（ui/AppRoot.kt:94-107）
LaunchedEffect(Unit) {                       // ← 只挂一次，不再随 notice 变化重启
    snapshotFlow { state.notice }
        .filterNotNull()
        .collect { text ->
            state.notice = null              // ← 在 collect 里改，不会重启本 effect
            hostState.showSnackbar(text)
        }
}

用 collect 而不是 collectLatest：showSnackbar 内部有互斥锁， 串行消费意味着短时间内的两条提示会依次显示，而不是把前一条掐掉 —— 对"保存失败"这类提示，丢失比延迟严重得多。

用户可感知差异证据风险
保存、导出、导入、删除、切换图标、清理图片等所有操作的成败提示从"看不见"变成正常显示； 错误提示终于能起到告知作用（此前用户只能靠界面状态猜） 修复前：
03:59:12.239 effect 启动 text=没有发现无用图片
03:59:12.276 showSnackbar 被中断：LeftCompositionCancellationException
修复后：
04:19:22.192 showSnackbar 正常结束 text=没有发现无用图片		 低。只改消费方式，不改状态语义；notice 仍是"一次性"的

P1#2「周期性提醒导出备份」从头到尾没有实现，但四处注释都在承诺它

现象.这个应用没有联网权限、没有任何自动上传、也没有云端副本 —— 用户不导出，"数据就只有一份"。而代码里到处写着"设置页会周期性提醒导出备份"，实际上一次都不会提醒。

根因.写入端一直在（导出成功时记时间戳），读取端从头到尾不存在：

SettingsStore.kt:141   state.settings.lastBackupReminderAt = System.currentTimeMillis()   // 唯一的写入
// 全工程 grep lastBackupReminderAt → 只有这一处 + 声明本身
SettingsStore.kt:123   const val BACKUP_REMINDER_INTERVAL = 7L * 24 * 60 * 60 * 1000        // 零引用

承诺它的注释有四处：BackupManager.kt:49（"所以设置页会周期性提醒导出"）、 SettingsStore.kt:91/122、ui/components/Common.kt:248（InlineNotice 注释里的"备份到期提醒"）。

修复.新增纯对象 vault/BackupReminder.kt（不依赖 Context，因此能在 JVM 单测里钉死边界）， 由 VaultAppState.enterUnlocked() 在每次解锁时判定，首页顶部渲染提示条、点击直达设置页。

核心判据（vault/BackupReminder.kt）
fun eval(lastExportedAt: Long, hasContent: Boolean, now: Long): Due {
    if (!hasContent) return Due.NONE                    // 空库不提醒：没东西可丢
    if (lastExportedAt <= 0L) return Due.NEVER_EXPORTED  // 有内容却从没导出过：立刻提醒
    if (now < lastExportedAt) return Due.NONE            // 系统时间回拨：宁可不提醒
    return if (now - lastExportedAt >= INTERVAL_MILLIS) Due.STALE else Due.NONE
}

为什么"从未导出过"要单独一档，而不是"没记录过就当成刚备份过"： 后者恰好放过了最危险的那批用户 —— 有数据、却从未备份。 实测把这条分支退回后，测试立刻报 expected:<NEVER_EXPORTED> but was:<NONE>。

超过 7 天未导出则换成"上次导出备份已经超过 7 天…"。空库不提醒，且与"条目损坏"告警条互斥（避免两条相似提示叠着出现）		 真机解锁后首页节点抓取：

P1#3 原图读取没有上限：大图先 OOM，再谈"校验"

现象.从相册选一张几十 MB 的全景图 / 扫描件 / RAW，应用可能直接崩掉；即便没崩， 提示也是"这张图片读不出来，换一张试试" —— 而用户换一百张也是同一个结果。

根因.读取环节无上限地往内存里堆字节，而那条 32 MiB 的校验发生在这之后：

改前（vault/ImagePipeline.kt）
val bytes = context.contentResolver.openInputStream(uri)?.use { stream ->
    ByteArrayOutputStream(1 shl 22).also { out -> stream.copyTo(out) }.toByteArray()
} ?: return null                      // 所有失败都收敛成一个 null
VaultSession.kt:392   require(plaintext.size <= MAX_IMAGE_PLAINTEXT_BYTES) { … }   // 校验在读取之后

内存已经花出去了，校验再准也拦不住 OutOfMemoryError （它是 Error，堆已经榨干，后续分配照样失败 → 应用崩掉而不是给出提示）。

改后（新增 vault/Streams.kt + ImagePipeline.prepare 返回三态）
internal fun InputStream.readCapped(limit: Int): ByteArray? {
    val out = ByteArrayOutputStream(minOf(limit, INITIAL_CAPACITY))
    val buffer = ByteArray(CHUNK)
    var total = 0
    while (true) {
        val read = read(buffer)
        if (read <= 0) break
        total += read
        // 先把"越界"判掉再写：否则最后一小段超限的字节也已经进了内存。
        if (total > limit) return null
        out.write(buffer, 0, read)
    }
    return out.toByteArray()
}

同时把"太大"与"读不出来"拆成两种可区分的结局（这本身就是扫描模式 2.4「无法区分的模糊判断」的实例）， 并让上限只有一个出处 —— ImagePipeline 直接引用 VaultSession.MAX_IMAGE_PLAINTEXT_BYTES， 两侧数字不可能再漂移：

sealed interface Preparation {
    data class Ready(val prepared: Prepared) : Preparation
    data object Unreadable : Preparation                     // 取不到流 / 不是图片 / 出错
    data class TooLarge(val limitBytes: Int) : Preparation { // 读完之前就放弃
        val message: String get() =
            "图片超过单张 ${limitBytes / (1024 * 1024)} MB 的上限，请先在系统相册里裁剪或缩小后再导入"
    }
}

同一类问题也出现在备份包里：BackupManager.inspect 用 zip.readBytes() 读清单， 没有任何上限 —— 而它是"选中文件之后、真正导入之前"的第一步，跑在 extract 那套 MAX_ENTRY_BYTES/MAX_TOTAL_BYTES 防护之前。已改为 readCapped(64 KiB)。

用户可感知差异证据风险
超大图片不再把内存吃光：选择后立刻告知"超过单张 32 MB 的上限，请先裁剪或缩小"，而不是崩溃或含糊的"换一张试试"； 照片库多选时还会说明"3 张因超过体积上限被跳过"，不再静默丢图 对照实验（8 MiB 输入 / 1 KiB 上限）：
退回修复后 → 超限后仍读走了 8388608 字节
修复后 → 读取量 ≤ 128 KiB 即停
清单条目（4 MiB）：退回后 清单被读走了 4194703 字节，修复后 < 512 KiB		 低。上限与写入侧同一个常量；"恰好等于上限仍可用"有正向用例兜住，不会把正常图片误判为超限

P2#4 桌面图标别名坏了无法自愈，而 verify() 正是那个"零调用的自检"

现象.伪装图标靠三个 activity-alias 互斥切换。apply() 刻意写成 "先启用目标、再禁用其它"（反过来会短暂出现"三个全禁用"，那一刻桌面图标消失）。代价是两步之间进程被杀 就会留下脏状态：桌面出现两个图标（伪装当场失效），极端情况下一个都不剩 （用户再也无法从桌面打开这个应用，只能去系统设置的安装列表里捞）。这两种状态都不会自愈，也不会有任何提示。

根因.判据 LauncherIcon.verify() 一直存在，但没有任何调用者。 用 tools/audit-scan.py 扫出来的正是这一条："定义了但从未被使用的成员函数"。

修复.VaultAppState.boot() 冷启动即自检，异常就修回来（VaultAppState.kt:780-805）：

private fun repairLauncherAlias() {
    val expected = settings.launcherAlias
    // 取不到状态时按"没问题"处理：宁可漏修，也不要在 PM 异常时反复写别名
    if (runCatching { LauncherIcon.verify(context, expected) }.getOrDefault(true)) return
    val repaired = runCatching {
        LauncherIcon.apply(context, expected)
        if (!LauncherIcon.verify(context, expected)) {
            // 记录里那个别名怎么都启用不了 → 退回 FPB：保证桌面上有一个能打开这个应用的入口
            LauncherIcon.apply(context, LauncherIcon.ALIAS_FPB)
        }
    }
    if (repaired.isSuccess) {
        launcherAlias = LauncherIcon.current(context)
        settings.launcherAlias = launcherAlias
    }
}

正常启动时 verify() 为真，一个 PackageManager 写操作都不发，不会引起桌面刷新。

P3#5 三个"零调用 + 注释承诺了不存在的用途"的常量

扫描器报出三个 const val 在生产代码里没有任何引用。它们的注释都在承诺某种用途， 而那些用途从未发生（与前两轮的 MAX_ENTRIES 是同一类病：注释描述的是"打算"，代码里是"没有"）：

常量注释承诺实际处理
SettingsStore.BACKUP_REMINDER_INTERVAL "距离上次提醒超过这个时长就再提醒一次导出备份" 零引用，提醒从未发生 删除，概念上移到 BackupReminder.INTERVAL_MILLIS（单一出处）
FpbLogo.FPB_WORDMARK_ASPECT "调用方按这个比例留位置就不会被拉伸" 零引用；且 FpbWordmark 内部已按自身比例居中（min(w/INK_W, h/INK_H)），本来就不会拉伸 —— 注释描述的问题不存在 删除（连同那条失实的注释）

二、本轮的元发现：五处缺陷有同一个形状

把五处缺陷摊开看，它们不是五种毛病，而是一种毛病的五种表现： 注释/命名描述的世界，与代码实际运行的世界不一致。

出处（注释/命名）承诺代码里的事实
BackupManager.kt:49、SettingsStore.kt:91/122、Common.kt:248"设置页会周期性提醒导出备份"时间戳只写不读，一次都不提醒
SettingsStore.lastBackupReminderAt名字是"上次提醒时间"实际写的是"上次导出时间"
LauncherIcon.verify()"供设置页做一次自检"零调用者，且判据本身把 DEFAULT 当 DISABLED
FPB_WORDMARK_ASPECT"按这个比例留位置就不会被拉伸"零引用，且组件本身已保证不拉伸
ImagePipeline.prepare 的调用点"读不出来会告知用户"读取无上限 + 把所有失败收敛成一个 null
这类缺陷为什么能长期存活：它们不会让任何一条测试变红，也不会让界面明显报错 —— 它们只是让某个"本该发生的事情"静静地不发生。唯一稳定的检出手段是 把注释当成断言、去代码里找它的实现，以及扫描"定义了但从未被调用"的成员。 这也是为什么本轮把 tools/audit-scan.py 的第一条扫描（2.1 定义了但从未被使用的常量/方法） 当成了主力工具：它命中了 3 / 5。

五、确认无误的部分

避免"只列问题 = 代码全是问题"。以下都是本轮逐行核对过、确认正确的关键设计：

项核对结论
AAD 绑定位置Aad.dekWrap(slot) / entryField(id, field) / blob(blobId) 把密文与"它该在哪"绑死，密文无法在位置间搬运。逐处核对调用点一致
清单行 id 派生manifestRowId() = HMAC-SHA256(DEK, "mixia:index:v1") 取前 16 字节 hex —— 真库与诱饵库共用一张表，靠 DEK 不同自然分域
写入原子性create/update/delete 全部走 rows.inTransaction { writeNote(); persistIndex() }，失败回滚内存索引
容量检查时机requireManifestCapacity(adding) 在动任何数据之前拒绝超限，而不是在事务里才失败
双库隔离purgeOrphanBlobs() 只删"能用当前域 DEK 解开"的孤儿，不会毁掉另一个库的图片
密钥文件写入先写 .tmp 再 renameTo（原子），失败时把刚生成的 DEK 就地销毁，绝不交给界面
恢复备份的前置与顺序强制锁定态（check(!session().isUnlocked)）→ 全程 cacheDir/restore-staging 暂存 → 先校验（密钥文件可解码且含 PRIMARY 槽、db 是 SQLite）→ 才 swapIntoPlace；替换顺序是"先让旧数据失去密钥文件、再放新数据"
zip 解析的输入防护safeEntryName() 拒 .. 与 \（zip-slip）；附件名必须过 RowIds.isValid；MAX_ENTRIES/MAX_ENTRY_BYTES/MAX_TOTAL_BYTES 三级限制
恢复后的生物识别处理导入必然清理 bio_wrap.bin 并置 biometricEnabled=false（硬件密钥在别的设备上，不可能匹配）
没有联网能力清单里不声明 INTERNET，可用 aapt2 dump permissions 独立验证
系统备份已关闭allowBackup="false" + fullBackupContent="false" —— 这是"数据只在本机"的硬保证，也是升级流程必须靠手动备份的原因

附：本轮的三个工具坑（都已写进脚本注释）

  • 并行编辑同一个文件会互相覆盖。同一文件的多处改动必须逐条串行执行；本轮一度出现"工具报成功、文件里却没有"， 造成一次构建失败（Unresolved reference 'BackupReminder'）。症状极具迷惑性。
  • run-as ... sed 's|...|...|' 里的引号会被 adb 的远端 shell 吃掉，模式永远匹配不上， 而 sed 匹配不上时既不报错也不改文件 —— 看起来像"改动被应用回写了"。改用"本地改好 → push → run-as cp"。
  • 测量方法本身会骗人。第一次验证提示条时只等了 1.2 秒就读日志，showSnackbar 尚未返回， 于是"没有结束日志"被误读成"修复没生效"。Snackbar 是 Short 时长（约 4 秒），必须等展示走完。
