审核方式是先写会失败的测试、跑出失败、再修，而不是"看一遍代码然后声称没问题"。为避免"改完才写的测试自然通过"这种自证， 另做了一次对照实验：把工程复制一份，只在副本里退回修复，跑同一套测试验证它们确实会红。

验证层次内容结果
对照实验（副本） 退回 4 处修改后跑同一套测试 5 / 20 失败 → 证明测试有效，不是空断言
修复前（工作区） 首次运行本报告新增的探测测试 8 / 13 失败 → 缺陷是测出来的
修复后 · 单元测试 JVM 上跑全部用例 132 / 132 通过（新增 20 条）
修复后 · 真机自检 Pixel_7 / API 37，真实 ART + Conscrypt + SQLite 19 / 19 通过
修复后 · 独立复核 把数据库文件拉回电脑，用 Python 逐字节搜明文 0 命中（20,544 字节）
为什么真机那一层不可省：单元测试跑在内存替身上，这次有一处修复（SQLite 事务）在生产代码里执行、却在单元测试里走不到。 如果只在电脑上跑测试，这处改动等于完全没验证过。真机自检里的「重新打开后条目与图片完整恢复」这一项， 恰好能判定事务是否真的提交了 —— 事务没提交，这一步必然失败。

二、缺陷清单

#级别位置缺陷后果
1P0 VaultSession.create 笔记行与索引清单两次写入各自独立提交，非原子 进程在两次写入之间被杀 → 笔记永久不可见且不被清理，用户无任何提示
2P0 VaultSession.delete 先删图片密文，再删行与清单 后续任一步失败 → 图片不可逆丢失，条目却还在
3P0 VaultKeyring.withExternalWrap 外部 KEK 写入槽位时缺少域校验 诱饵 DEK 可被写进主密码槽 → "输着真密码进假库"，私密内容写进准备给人看的库
4P0 NoteIndexCodec.encode 条目数上限只拦解码、不拦编码 超过 10 万条时清单顺利落盘却再也解不回来 → 每次解锁都拒绝，数据彻底锁死
5P1 KdfParams.init 内存开销与迭代次数只有下界、没有上界 伪造的备份文件可让解锁抛 OutOfMemoryError（属 Error，catch(Exception) 接不住）或永久卡死
6P1 Base32Crockford.decodeOrNull 合法恢复码后多打一个 0 仍被接受 同一恢复码存在无穷多个等价写法，违反"长度不符即拒绝"的契约
7P1 VaultKeyFileCodec.decode 不校验槽位密文长度；重复槽位号静默覆盖 结构非法的密钥文件被接受，把"文件损坏"伪装成"密码错误"
8P1 NoteCodec.readString / readList 按长度字段预分配内存，未对照剩余字节数 几十字节的输入即可触发最大 4 MB 分配（内存放大）
9P2 NotePayload.normalized 先去重、后截断 仅在第 32 字符后不同的标签截断后重复 → 界面出现重复标签、计数错误
10P2 VaultSession.update 未调用 requireUnlocked() 锁定时静默返回 null，调用方误判为"条目不存在"（delete 却抛异常，同类两套语义）
11P2 VaultSession.unlock 首行无条件调用 lock()，会先发出一次 LOCKED 回调 重复解锁时回调序列变成 LOCKED→UNLOCKED，界面闪回解锁页
12P2 FileBlobStore 崩溃残留的 .part 文件无人回收 不满足 id 形状 → listIds() 看不见 → 孤儿清理永远扫不到，永久占空间
13P2 InMemoryBlobSink.read 测试替身返回内部实例而非副本（与 write 不一致） 测试里一次就地修改会直接改到"落盘"内容，可能掩盖真实缺陷

三、逐条详情

#1 写入不是原子的：笔记行与索引清单各自提交 P0

VaultSession.kt · create() / update() / delete()
改前
val id = idFactory()
writeNote(id, normalized)      // 第 1 次提交
indexPut(id, normalized)
persistIndex()                 // 第 2 次提交 —— 中间被杀就完了
改后
indexPut(id, normalized)       // 内存先更新（persistIndex 依赖 index.keys）
try {
    rows.inTransaction {       // ← 两次写入合成一次原子提交
        writeNote(id, normalized)
        persistIndex()
    }
} catch (t: Throwable) {
    indexRemove(id)            // 落盘失败则连内存一起撤回
    throw t
}
用户感知差异
改前：应用被系统回收的瞬间若正好在写盘，会出现"我明明记过的内容不见了"，且此后永远找不回、磁盘空间也一直被占着。 改后：要么完整写入，要么完全没写 —— 用户最多重记一次，不会留下"幽灵数据"。
风险
这是"数据只存在本机"类应用最不能接受的故障类型：静默、不可逆、无法归因。 触发条件（低内存被杀、用户划掉任务、系统回收）在日常使用中并不罕见。

风险
笔记正文可以从别处誊抄，已加密的照片删掉就是没了。 删除顺序应当按"可恢复性"从低到高排，而不是按直觉的"先清大文件"。

#5 KDF 参数没有上界：伪造备份文件可致崩溃 P1

KdfParams.kt · init 块（参数来源是密钥文件，M5 导入功能的入口）
改前
require(memoryKiB >= MIN_MEMORY_KIB) { "内存开销过低：$memoryKiB KiB" }
require(iterations >= 1) { "迭代次数至少为 1" }
// 没有上界
改后
require(memoryKiB in MIN_MEMORY_KIB..MAX_MEMORY_KIB) { ... }   // 上界 1 GiB
require(iterations in 1..MAX_ITERATIONS) { ... }                // 上界 64

const val MAX_MEMORY_KIB = 1024 * 1024
const val MAX_ITERATIONS = 64
用户感知差异
正常使用无感（预设三档最高 256 MiB / t=4，远在上界内）。 差别在于：从网盘下载一个被构造过的备份包导入时，改前是应用当场闪退且给不出原因， 改后是抛出一句可理解的"内存开销越界：2147483647 KiB"。

#6 恢复码的"等价别名"：多打一个 0 也能解开 P1

Base32Crockford.kt · decodeOrNull()（影响 VaultKeyring.unlockWithRecoveryCode）
改前
if (bitsLeft > 0 && buffer != 0) return null        // ① 残留位全为 0 就放过
if (expectedBytes != null && written != expectedBytes) return null   // ② 只看解出几个字节

// 于是：48 字符恢复码 + 一个 '0'
//   → 245 位，解出仍是 30 字节（② 通过）
//   → 多出的 5 位恰好是 '0' = 00000（① 通过）
//   → 输入被接受，多打的字符被静默吞掉
改后
if (expectedBytes != null) {
    if (written != expectedBytes) return null

    // 反查规范化：挡掉"字节数对得上、字符数却多出来"的别名输入。
    // normalize() 已把输入归一到规范大写，因此这次比较同时覆盖了字符数是否正确。
    if (!encode(out).contentEquals(cleaned)) return null
}
用户感知差异
正常抄对 48 字符 → 无差别。抄错长度（多打、少打）→ 改前偶发"竟然能过"，改后稳定报"恢复码无效"。 这不会让正确输入被拒（48 字符 240 位整除 5，任何合法输入的往返编码都等于自身）。
风险
密码学上没有削弱（解出的仍是同一把 DEK），危害在于契约失效： "长度不符即拒绝"这条规则被绕过，输入框的即时校验也就失去了意义。 恢复码是"用户会手抄、手输"的东西，这一类宽松必须是零。

#11 重复解锁会先发一次 LOCKED 回调 P2

用户感知差异
无（只影响测试）。但它是一个"测试假通过"的来源： 测试里一次不经意的就地修改会直接改到存储内容，让断言失去意义。
风险
与 #1 同一类问题的一体两面 —— 测试替身的语义必须和生产实现一致，否则它掩盖的正是它该暴露的东西。 顺带说明：这次为 #1/#2 加的 InMemoryRowStore.inTransaction 是真实的快照回滚而不是空实现， 因为替身若不回滚，"写入原子性"这条测试即使生产代码是错的也会通过。

四、未修改但需知晓的 6 项

以下是审核中发现、但刻意不改的点。它们要么是有明确理由的设计权衡，要么归属 M3/M5 的界面与管线工作。

项现状为什么现在不动
清单行缺失 = 全新库
VaultSession.loadIndex		 清单行不存在时一律当作空库，不报"不可读"。 不可修的模糊判断。真库与诱饵库的行混在同一张表里、形状完全一致，"清单丢了"和"这是新库"在字节层面无法区分。 若改成"库里有行就拒绝解锁"，会直接误伤诱饵库第一次被打开的场景（真库有行、诱饵库还没写过 → 假密码打不开）， 等于把胁迫防护废掉。真正关掉这个窗口的是 #1 的写入原子性。已在代码里写明这段权衡。
AAD 拼接歧义
Aad.entryField		 "mixia:v1:entry:$id:$field"，若 id 本身含 :，两组不同的 (id, field) 会产生相同 AAD。 当前所有 entryId 都来自 RowIds（严格 32 位十六进制），不可达。 但接口本身没有约束 —— M3/M5 若在此处传入非 id 值需注意。建议后续给长度加前缀或加 require。
会话非线程安全
VaultSession		 index / searchCache 无同步。 按设计应由界面层单线程访问。M3 必须把会话访问收敛到单一调度器，不要直接在主线程外的多个协程里并发调用。
图片字节数无上限
VaultSession.putImage		 任意大小的字节都能加密入库。 重编码与压缩属 M3 的图片管线职责（长边 2048 / JPEG q85）。建议管线里同时设一个体积硬上限（如 20 MB），防止一次误操作写入超大 blob。
搜索每按键全量排序
VaultSession.search		 每次调用都走 notes()：新建列表 + 全量排序，再过滤。 几百条无感，几千条会有可感知的延迟。建议 M3 把"已排序列表"缓存起来，写入时失效。
release lint 门禁仍关闭
app/build.gradle.kts		 checkReleaseBuilds = false。 本机只有 JDK 25，AGP 8.7.3 的 Lint 解析版本号时崩溃（IllegalArgumentException: 25.0.2）。属已知环境问题，M7 装 JDK 21 或升 AGP 后重新开启。
